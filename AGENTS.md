# Product factory

Home of the shared agent core (`core/`) and the place where new products are made. Every new product starts from
a fresh base project (built from the core's base spec), then goes through intake, requirements, product review,
prototype, stories, design, build, review, audit and release with the user deciding at fixed gates (product mode,
`factory` skill). Changes to an existing product run as tasks (task mode, `sdlc` skill), either in that product's
own repo (the core is installed there by `base-builder`) or from here with `--root <product root>`.

## Repo map
| Path | What |
|---|---|
| `core/` | the agent core source (plugin layout): agents, skills, hooks, scripts, reference, templates; `core/core-plan.md` is its design, `core/migration/` the notes for moving other repos onto it |
| `plugin/` | the Claude Code plugin `product-factory` (by TalenTeam Product & Engineering), built from `core/` by `core/scripts/build_plugin.py` (never edited by hand); `.claude-plugin/marketplace.json` makes this repo the `talenteam` marketplace |
| `.github/` | the sync bot: `workflows/core-sync.yml` and `core-sync/` (script, target repos, AWS role policies); on a push to `main` it installs the core into each product repo |
| `.claude/` | the core installed for this repo (`install.py`), plus `project.json` (work folder `work`, products under `D:/products`, read-only `D:/skillos`) |
| `work/<slug>/` | one folder per product or task: every document, question and decision, and its live status |
| `D:/products/<slug>/` | the product roots (code), outside this folder |
| `standards/`, `base/`, `scripts/` | legacy copies kept for the DeskBook run; the core's own copies are in `core/reference/` and `core/scripts/` |

## Hard rules
1. Git: no command that changes a repo (commit, push, pull, merge, stash, reset, switch, checkout, add, ...); read-only
   git is fine. `git pull` only when the developer asks for it in their own message. The developer does git (this folder is the
   public GitHub repo `zakvantalenteam/product-factory`; a push to `main` ships the core to every product repo).
2. Never start or restart servers. Say what needs a restart and why. The one exception is the live-status page
   (`live-status` in `.claude/launch.json`).
3. Repos used as reference (for example `D:\skillos\repo\SkillsOS`) are read-only: `git show`, `git ls-tree`,
   `git grep`, Read only.
4. Secrets: never copy values from `application*.properties`, `manifest.yml`, `xs-security.json` or `*Constants*`
   files into code, docs or chat. Use placeholders.
5. Product-owner documents: short, plain words, the gap or issue highlighted first, no jargon
   (`.claude/core/reference/review/plain-english.md`); each also gets an offline HTML copy
   (`python .claude/core/scripts/md_to_html.py <file.md>`).
6. Replies to the user: 6 lines or fewer unless asked, plain words, end with one status line and `Next:`.
7. The core is changed only in `core/`; then `python core/scripts/install.py .` installs it here and
   `--check` must be clean. Every other repo gets the same version with the same command, in the same change:
   product-factory, Blend, TalentBox and the plugin stay in sync (SkillsOS uses the plugin, no repo install) unless the developer asks for a change in one
   project only (then it goes in that project's own files and the reply says which projects differ).

## How work flows (agent core - managed by install.py, do not edit between the markers)
Triage every request first (`sdlc` skill), without asking which lane:
- **Answer**: questions, "discuss", "explain" - answered directly (big searches go to `explorer`). "plan", "review this" and "don't change" change no code.
- **Quick fix**: obvious and small (up to ~30 lines in up to 3 files, nothing to decide) - routed to its area agent with a quick brief (the exact files and lines, the fix, the test; about 8 calls, no context pack), then `python .claude/core/scripts/live_status.py quick "<what>"`.
- **Setup work**: changes to the AI setup only (`.claude/`, `.cursor/`, `AGENTS.md`, `CLAUDE.md`, `setup_paths`) - done by the main session, no task; run `python .claude/core/scripts/cursor_sync.py`, then `--check` must be clean.
- **Task** (task mode): every other change to an existing product - a task in the work folder (`work_dir` in `.claude/project.json`). First `explorer` writes the context pack (`context.md`: impact map with every caller, endpoint, screen and outside node as `path:line`, key code, the rules that apply, risk signals); the risk (low, medium, high) is set from that evidence; then only the agents the task needs, each reading the pack instead of exploring again; Build goes to the area agents (`backend-developer` for Java, `frontend-developer` for UI, `integration-engineer`, `n8n-expert` for workflows, `devops-engineer` for build and deploy files, `qa-engineer` for tests), independent parts with no shared files in parallel in one message. The risk sets the safety net, so nothing else breaks: compile and the full unit suite before and after, every changed file planned (scope check); at medium and high also characterization tests that lock today's outputs, every caller checked and the smoke list of each area touched (`.claude/smoke.md`). Every review MUST adds a line to `.claude/review/lessons.md`. QA signs off every task that changes code: `qa-lead` plans the tests at Design (a risk-based matrix of criterion, test type, role and data volume) and signs off at Test, `ui-qa-expert` tests every UI change in the running app against the UI checklist (`.claude/core/reference/qa/ui-checklist.md`: every state, paging at scale, the detail in view, cut-off text readable, keyboard, 360 px, 200% zoom, long labels, tenant colours, console and network), `e2e-qa-expert` runs the journeys across roles, `qa-engineer` writes the tests and runs the API checks; a checklist MUST fails Test, and no task closes without the sign-off. Automated tests always go in the project's test folder, mirroring the package of the code under test (Java `src/test/java/<same package>/`), never in `src/main/**` or the repo root; the scratchpad holds only throwaway scripts.
- **Product** (product mode): an idea, a PRD or "build a new product" - never built straight from the document: the `factory` skill runs intake, base, requirements, product review, prototype, stories, design, build, review, audit and release with a gate at each decision.

The main session is the Tech Lead: it triages, decides, briefs, routes, integrates and verifies, and never writes product code (everything outside the AI setup and the work folder); it keeps triage, the gates and decision cards, quick live checks in the browser (the UI and E2E QA experts test in their own browser tabs), the final checks and setup work. The team is picked by need, not by size; a stage with nobody on it is skipped. The developer (or product owner) is stopped only for something to decide: gaps in the brief, decision cards D1-D8 (scope, data model, API, access, UI, dependencies and config, other owners, go-live) and prototype picks - one gate per stage, with its full text in the chat and an Approve/Change question. Hooks enforce the flow in Claude and Cursor: the guard holds data-model, access and config edits until their card is approved, blocks the main session's edits to product code (Claude Code; Cursor's hooks cannot tell the main session from an agent, so there the rule and the live page's chip hold it), blocks git commands that change the repo (pull passes only when the developer asked for it) and generated files, and (product mode) blocks product code before the base stage or the design approval; a rules check runs after each edit; a turn that changed files outside these lanes is sent back once. The reviewer fails any change with a MUST from the review checklists. The live page shows every task at agent level and is the only tracker (never make another tracker page or artifact): each agent's work on its own card, the Tech Lead's decisions and routing on its card (with a chip when it edited product code itself), and the Tech Lead's share of the work. Open it with `python .claude/core/scripts/live_status.py open <id>`.

## Agents and skills (agent core)
- Flow skills: `sdlc` (triage, task mode), `factory` (product mode), `prototype`, `dev-handoff`, `commit-msg`, `verify-push`, `live-check`.
- Agents: `explorer` (search), `spec-analyst`, `bug-investigator`, `product-critic`, `story-sizer`, `ux-designer`, `solution-architect`, `data-architect`, `security-architect`, `base-builder`, `backend-developer`, `frontend-developer`, `integration-engineer`, `devops-engineer`, `performance-engineer`, `code-reviewer`, `qa-lead`, `qa-engineer`, `ui-qa-expert`, `e2e-qa-expert`, `verifier`, `audit-expert`, `release-manager`; domain experts `sf-expert`, `sf-skills-expert` (SuccessFactors job profiles and skills), `ai-engineer`, `n8n-expert` (repo facts in `.claude/experts/`). This repo's own agents, area skills and path rules sit next to them.
- Every agent is tagged with verified credentials (frontmatter `certifications:`, general first, then SAP) and works to their practical knowledge: its practice pack `.claude/core/reference/practice/<agent>.md` and its `## Expert standard` (the simplest good solution, no new layer or dependency without a stated need; rules marked (SAP) apply only when `stack.platform` is `sap-btp`). It reads `.claude/core/reference/agents/common.md`, its practice pack and the task's `context.md` first (code agents also the stack packs `.claude/project.json` `stack` names), writes its output file first (it opens with `## Summary for people` and a `## Plan`: a Goal, Output and Done when line for this task, then 4-8 items it ticks as it goes, each naming a file, endpoint, node, screen, criterion or decision; the live page shows both and flags a generic plan), uses about 35 tool calls if it decides (spec, investigation, audit, domain experts, data and security design) or about 20 otherwise (`code-reviewer` and `solution-architect` work from a pack: `review_pack.py`), web lookups only for version-specific facts (at most 3, agents with a web tool), and replies in 10 lines or fewer. Reviewers are read-only. Models (each agent's `model:` line): Opus for the agents that decide (`solution-architect`, `security-architect`, `data-architect`, `ai-engineer`, `code-reviewer`, `ux-designer`, `spec-analyst`, `product-critic`, `bug-investigator`, `audit-expert`, `performance-engineer`, `sf-expert`, `sf-skills-expert`, `n8n-expert`, `qa-lead`, `ui-qa-expert`), Sonnet 5.5 for the ones that build and check (`backend-developer`, `frontend-developer`, `integration-engineer`, `devops-engineer`, `base-builder`, `qa-engineer`, `e2e-qa-expert`, `verifier`, `explorer`, `release-manager`, `story-sizer`); `maxTurns` is about 1.5 times the call budget. Cursor runs every agent on the session's model.
- No git command that changes the repo (commit, push, pull, fetch, merge, rebase, stash, reset, checkout, switch, restore, add, branch, tag, ...); read-only git (status, diff, log, show) is fine. `git pull` only when the developer asks for it in their own message. Never start or restart servers (say what needs a restart and why); never copy secret values.
- Core files (`.claude/core/`, the core agents and skills listed in `.claude/core/core.lock`) are changed only in the core source and installed with its `install.py`; `python .claude/core/scripts/install.py . --check` lists hand edits.
- All projects stay in sync: every project with the core (product-factory, Blend, TalentBox and any product made since) and the product-factory plugin run the same core version; SkillsOS uses the plugin and gets no repo install. A change to the shared setup (an agent, skill, hook, script, rule or the flow) is made once in the core source (product-factory `core/`) and installed in every project in the same change: `python core/scripts/install.py <repo> --write-settings` from product-factory for each, then `install.py . --check` and `cursor_sync.py --check` clean in each. Only when the developer asks for a change in one project does it go in that project's own files (its `.claude/project.json`, its own agents, skills and rules, AGENTS.md outside the core block), never in a core file, and the reply says which projects now differ. In a repo without the core source, say the change belongs in product-factory's `core/` and which projects it reaches.
- Claude Code reads this file through `CLAUDE.md`; Cursor reads it directly and loads `.claude/skills/` itself. The Cursor agents, rules and hooks in `.cursor/` are generated by `cursor_sync.py`; every setup change must keep working for Cursor in the same change.
